New Components

N-01 H264Encoder — RGB frames → H.264 NAL bytes in-place new include/stream/h264_encoder.hpp · src/stream/h264_encoder.cpp
Why
Raw RGB streaming (Phase 1) sends ~2.8 MB per frame at 1280×720. At 30 fps that is ~84 MB/s — far beyond any realistic LAN or localhost buffer. H.264 at 4 Mbps compresses the same frame to ~17 KB, a 165× reduction. libx264 with ultrafast/zerolatency preset encodes a 1280×720 frame in <1ms on a modern CPU, making real-time encoding viable.
Design Decisions
  • pImpl idiom — FFmpeg types (AVCodecContext, AVFrame, etc.) are hidden inside struct Impl. Including FFmpeg headers in h264_encoder.hpp would force every translation unit that includes it to also find FFmpeg, breaking the Phase 1 / Phase 2 separation.
  • In-place transform — encode(Frame&) replaces frame.pixels with NAL bytes and updates frame.compression, frame.width, frame.height. This lets the encoder slot into the existing SenderPort<Frame> pipeline without a separate buffer.
  • Single sws pass — sws_getContext is configured to convert and rescale in one call (RGB input_w×h → YUV420P enc_w×h). On retina displays, this combined pass handles the 2×→1× downscale at zero extra cost.
  • repeat_headers=1 — Embeds SPS+PPS parameter sets before every IDR frame. Without this, clients that connect mid-stream can never decode because they miss the parameter sets that were only in the first packet.
  • gop_size = fps/2 — An IDR keyframe every 0.5 s ensures a newly connected client recovers within half a second. The original roadmap suggested intra-refresh=1, which was removed: intra-refresh replaces IDR frames with progressive refresh, which eliminates the resync point that late-joining clients depend on.
  • No slice-max-size — slice-max-size=1500 is an MTU hint for UDP transport. On TCP, the transport layer handles fragmentation. Using it produces 40–70 slices per frame at 1280×720, exceeding the Conan-built FFmpeg decoder's hardcoded MAX_SLICES=32 limit and triggering decode warnings on every frame.
  • max_b_frames=0 — B-frames introduce display-order vs decode-order reordering which adds latency. Zero B-frames keeps PTS==DTS for truly low-latency output.
N-02 H264Decoder — H.264 NAL bytes → raw RGB pixels new include/stream/h264_decoder.hpp · src/stream/h264_decoder.cpp
Why
The client receives Annex B NAL bytes over TCP and must convert them back to raw RGB pixels for OpenGL texture upload. FFmpeg's libavcodec provides the H.264 decoder; libswscale converts YUV420P (the decoded pixel format) back to RGB24.
Key Design Decision — No AVCodecParserContext
An earlier implementation used AVCodecParserContext to split the incoming byte stream into individual NAL units before feeding them to the decoder. This caused non-existing PPS 0 referenced / decode_slice_header error messages on every single frame.

Root cause: The parser maintains state between calls. Our framing protocol already delivers one complete encoder output blob per frame — the blobs are perfectly framed at the TCP level. Feeding a pre-framed blob through a stateful parser confused the parser's internal NAL boundary detection.

Fix: Feed the padded blob directly to avcodec_send_packet without any parser. FFmpeg's decoder handles Annex B start codes internally. The parser layer is only needed for unframed raw byte streams (e.g. reading a raw .h264 file with no container).
Lazy sws reinit on resolution change
The SwsContext is recreated only when the decoded frame dimensions change. This handles server-side resolution changes at runtime without requiring a full reconnect. In steady state (fixed resolution), no allocation happens per frame.
N-03 FFmpeg log bridge — route av_log through spdlog logging include/stream/ffmpeg_log.hpp · src/stream/ffmpeg_log.cpp
Why — Root Cause of Missing Logs
FFmpeg's av_log system is completely separate from spdlog. By default it calls fprintf(stderr, ...) directly. This means all FFmpeg messages ([h264 @ ptr] non-existing PPS, swscaler: No accelerated colorspace, etc.) go to the terminal's stderr and are never written to encode_server.log or decode_client.log.
What Changed
install_ffmpeg_log_bridge() replaces FFmpeg's default stderr callback with a custom one that:
• Drops AV_LOG_VERBOSE and below (avoids flooding logs with per-frame debug output)
• Maps AV_LOG_ERROR → spdlog::err, AV_LOG_WARNING → spdlog::warn
• Uses av_log_format_line2 to preserve the [h264 @ ptr] context prefix FFmpeg adds
• Strips the trailing \n FFmpeg always appends
• Routes the message through Log::get("ffmpeg"), which writes to both the file sink and the ImGui log panel
• Uses std::call_once so it is safe to call from multiple init paths
After this change
FFmpeg errors and warnings now appear in encode_server.log, decode_client.log, and the in-app ImGui "Log" panel under the logger name [ffmpeg].
N-04 encode_server — Phase 2 server application new app/encode_server.cpp
Why
The Phase 1 stream_server sends raw RGB pixels. Phase 2 needs a server that encodes each captured frame to H.264 before transmission. A separate executable keeps Phase 1 runnable and unmodified.
Notable Design Choices
  • vsync OFF — glfwSwapInterval(0). With vsync ON, glfwSwapBuffers blocks until the next display refresh (~16.7ms at 60Hz). The capture+encode runs before the swap, so a slow encode eats into the frame budget and causes missed vsyncs, dropping throughput to 5–6 FPS. Disabling vsync lets the loop run as fast as the hardware allows; the target FPS is enforced by a manual timer.
  • Lazy encoder init — The encoder is initialized on the first captured frame so it knows the actual framebuffer dimensions. This avoids a race with the GLFW window not yet having a valid framebuffer at startup.
  • glfwGetWindowSize for logical size — On retina, glfwGetFramebufferSize returns 2× physical pixels. The logical size is what the encoder should target, since the client renders at logical resolution.
N-05 decode_client — Phase 2 client application new app/decode_client.cpp
Why
The Phase 1 stream_client displays raw RGB textures directly. Phase 2 needs a client that receives H.264 NAL bytes and decodes them before display. The decode hook (set_decode_fn) inserted into GlFrameTexture::update keeps the networking and display code identical to Phase 1.
N-06 start_encode_stream.sh — launch both processes new script/start_encode_stream.sh
Why
Running encode_server and decode_client manually in two terminals is tedious. The script launches both from build/Debug/ (so log files land in the right directory), traps SIGINT/SIGTERM to kill both on Ctrl+C, and uses wait -n to exit when either process finishes naturally.

Bug Fixes in Existing Code

F-01 Frame::valid() always returned false for H264 frames fix src/stream/frame_protocol.cpp
Bug
Frame::valid() called expected_size(), which returns width × height × bytes_per_pixel. For a compressed frame (compression != None), there is no fixed expected size, so expected_size() returned 0. valid() then required pixels.size() == 0, which was never true for a real H264 frame, so every H264 frame was rejected by the receive path.
Fix
+if (compression == Compression::H264)
+    return !pixels.empty() && pixels.size() <= max_frame_payload_size;
 const size_t expected = expected_size();
 return expected > 0 && expected <= max_frame_payload_size && pixels.size() == expected;
F-02 GlFrameCapture — encode hook + FBO blit for retina performance perf new API include/stream/gl_frame_capture.hpp · src/stream/gl_frame_capture.cpp
Performance Problem
On macOS Retina displays, glfwGetFramebufferSize returns 2× the logical window size. A 1280×720 window has a 2560×1440 physical framebuffer. Before this fix, glReadPixels(0, 0, 2560, 1440) transferred 11.06 MB every frame across the GPU-CPU bus — the single biggest bottleneck, limiting throughput to ~5 FPS regardless of how fast the H.264 encoder was.
Fix — GPU-side blit before glReadPixels
set_target_size(logicalW, logicalH) tells the capture system the desired output resolution. When the physical framebuffer is larger:
  1. An internal FBO (GL_FRAMEBUFFER + renderbuffer at target size) is created lazily.
  2. glBlitFramebuffer downscales from the default framebuffer (2560×1440) to the FBO (1280×720) entirely on the GPU — zero CPU cost.
  3. glReadPixels reads from the small FBO: 2.76 MB instead of 11 MB.
This is a 4× reduction in GPU→CPU transfer, which proportionally removes the main frame-rate bottleneck on retina hardware.
Encode hook
set_encode_fn(std::function<bool(Frame&)>) registers a callback that is called after glReadPixels but before frames_.deliver(). The callback transforms the frame in-place (RGB → H264 NAL bytes). The preview texture is uploaded to ImGui before the encode callback runs, so the server's "Captured Preview" window always shows the raw RGB image regardless of encoding.
F-03 GlFrameTexture — decode hook + upload_rgb refactor new API include/stream/gl_frame_texture.hpp · src/stream/gl_frame_texture.cpp
Why
The original GlFrameTexture::update() only handled Compression::None frames. H264 frames were silently dropped. A decode hook keeps FFmpeg out of stream_core (which must remain FFmpeg-free) while giving Phase 2 apps a clean integration point.
What Changed
  • Added set_decode_fn(std::function<bool(const Frame&, Frame&)>) — callback receives the H264 frame and writes decoded RGB into an output frame.
  • Extracted upload_rgb(const Frame&) private helper — uses glTexSubImage2D when the resolution hasn't changed (avoids GPU texture reallocation every frame) and glTexImage2D only on first use or resolution change.
  • update() now dispatches: H264 frame → decode_fn_ → upload_rgb; raw RGB frame → upload_rgb directly.
F-04 Log::get() — flush on every write to prevent log loss on SIGTERM fix logging include/mylib/log.hpp
Bug
spdlog::basic_file_sink_mt uses buffered I/O internally. The start_encode_stream.sh script kills encode_server with SIGTERM when either process exits. SIGTERM's default handler calls _exit(), which does not flush C++ stream buffers or run destructors. Result: encode_server.log was always empty. The decode_client exited naturally (user closed window), allowing its destructor to flush, so decode_client.log had content.
Fix
 auto logger = std::make_shared<spdlog::logger>(name, sinks.begin(), sinks.end());
 logger->set_level(inst.m_level);
+logger->flush_on(spdlog::level::trace); // write-through so SIGTERM doesn't lose messages
 inst.m_loggers[name] = logger;
flush_on(trace) tells spdlog to call fflush() on the underlying file after every single log message. This is a write-through mode: each message is on disk immediately, so a sudden process kill cannot lose recent log entries. The performance cost is negligible for a debug/development tool that logs at human-readable rates.

Known Behaviors (Not Bugs)

Observation Explanation Severity
[ffmpeg] [error] non-existing PPS 0 referenced (2–3× at stream start) When the client connects, it may land mid-GOP and receive P-frames before the next IDR. With gop_size = fps/2, the next IDR arrives within 0.5 s and decoding recovers automatically. This is inherent to any live streaming protocol — the first viewer always misses some frames. Cosmetic — self-resolving
[swscaler] No accelerated colorspace conversion found from yuv420p to rgb24 The Conan-built FFmpeg on ARM64 (Apple Silicon) has no NEON-vectorized YUV420P→RGB24 path. It falls back to a scalar loop. This appears once per stream when the SwsContext is first created. No functional impact; performance impact is minimal for this one-shot conversion. Informational only
