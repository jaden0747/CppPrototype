Architecture Decisions

D-001 Phase scope — which feature set to implement Architecture
Question: Implement Phase 1 (raw BGR over TCP) or Phase 2 (H.264 encoded)?
Options:
Phase 1 — raw RGB over TCP Phase 2 — H.264 + libx264
Rationale: Phase 1 isolates the producer-consumer loop without codec complexity. Raw frames are uncompressed and easy to inspect. H.264 (Phase 2) will be trivially addable on top once the transport layer is solid. The purpose here is understanding the pipeline, not achieving broadcast-quality compression.
D-002 Video source — what the server captures Rendering
Question: What pixel data should the server stream?
Options:
glReadPixels — own OpenGL framebuffer ScreenCaptureKit (macOS 12.3+) OpenCV webcam Synthetic test pattern
Rationale: glReadPixels requires zero new dependencies — the project already has OpenGL via GLFW. It captures the server's own rendered ImGui window, which gives an interesting recursive "mirror" effect (the client sees the server's UI). This mirrors how Sunshine captures the GPU framebuffer before sending. No Objective-C bridging (ScreenCaptureKit) or new Conan packages (OpenCV) needed.
Trade-off: glReadPixels is synchronous (stalls GPU pipeline). For Phase 1 this is fine; Phase 3+ would switch to async PBO (Pixel Buffer Object) readback.
D-003 Resolution — fixed vs dynamic Network
Question: Stream at a fixed resolution or whatever the GLFW window is?
Options:
640×480 fixed 1280×720 fixed Dynamic — match framebuffer size, embed w/h in header
Rationale: Dynamic resolution is more realistic (mirrors real streaming protocols). The three extra bytes in the per-frame header (8 bytes for w+h) are negligible vs frame payload (~2.7 MB at 1280×720). It also handles Retina displays correctly because we use glfwGetFramebufferSize (not window size), which gives physical pixels.
D-004 Network transport — TCP socket implementation Network
Question: POSIX sockets vs ASIO (already in Conan) for the TCP layer?
Options:
POSIX sockets (sys/socket.h) + _WIN32 stubs ASIO synchronous
Rationale: Phase 1 in the requirements doc uses raw POSIX sockets — keeping the learning artifact consistent with the material. ASIO adds another layer of abstraction that obscures the actual syscalls. The stream_server/client don't need the event-loop facilities ASIO provides. Windows compatibility is handled with a thin #ifdef _WIN32 block (WSAStartup + SOCKET type).
D-005 Threading model — render vs network Architecture
Question: How do we decouple the render loop (60 FPS) from the network send (limited by bandwidth)?
Chosen: Single SharedFrame struct with mutex + condition_variable. Render thread writes latest frame and sets hasNew=true, then notify_one. Network thread waits with wait_for(200ms) so it can check g_running on timeout. If the render produces a new frame before the network thread finishes sending the last one, the old frame is simply overwritten (latest-wins). This matches real streaming behaviour: you never want to show a stale frame.
Trade-off: Copying up to ~2.7 MB while holding the mutex briefly stalls the render thread. For Phase 1 (local loopback) this is <1ms and invisible. Phase 2+ should use a triple/ring buffer.

D-007 Server UI — what panels to show Rendering
Chosen panels:
1. Server Control — connection status, client IP, frames sent, bytes sent, render FPS.
2. Captured Preview — ImGui::Image of the last captured framebuffer. Creates a recursive mirror effect (the preview shows a thumbnail of itself from the previous frame). This is intentional and demonstrates the pipeline visually.
Rationale: The preview confirms what is actually being sent. The mirror-inside-mirror effect is a natural side-effect of capturing the server's own window and is interesting for learning.
D-008 Vertical flip — OpenGL origin correction Rendering
Problem: glReadPixels returns pixels with origin at bottom-left. Standard image format (and what the client expects) is top-left origin.
Fix: After glReadPixels, flip the pixel buffer vertically using std::swap_ranges on row pairs. O(height/2 × width × 3) — for 1280×720 this is ~1.4M swap operations, well within a single frame budget on modern hardware.
D-009 SIGPIPE handling on macOS/Linux Network
Problem: Writing to a disconnected TCP socket raises SIGPIPE and kills the process by default. MSG_NOSIGNAL flag (Linux) doesn't exist on macOS.
Fix: Call signal(SIGPIPE, SIG_IGN) once in main(). The send() call then returns -1 with errno=EPIPE instead of killing the process. We detect this in our send_all helper and cleanly close the client socket.
D-010 Build system integration Build
New targets added to CMakeLists.txt: stream_server and stream_client. Both link only against the already-present imgui, glfw, OpenGL::GL, and Threads::Threads. No new Conan packages required.
