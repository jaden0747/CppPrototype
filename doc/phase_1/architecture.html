Phase 1 — Stream Pipeline Architecture

Raw RGB over TCP  ·  two-process, two-thread-per-process  ·  No encoding  ·  ~60 FPS target

Phase 1 stream_server ✓ stream_client ✓ start_stream.sh ✓ Settings ✓ Logging ✓ Data Ports ✓

1System Topology

Two independent OS processes launched by script/start_stream.sh. All inter-process communication is via TCP. Within each process, frames and stats flow between threads through data ports (Mempool + SenderPort + ReceiverPort) — zero-copy, no manual mutex management. The server adds a condition_variable so the net thread can block efficiently rather than polling.

2Server Thread Model

2a. Render Thread → FrameData ports → Net Thread (sequence)

sequenceDiagram autonumber participant RT as Render Thread participant FP as Frame Port participant CV as frameCv participant NT as Net Thread participant SP as Stats Port Note over RT: Setup — frameSender.connectMempool, frameReceiver.connect, statsReceiver.connect Note over NT: Setup — statsSender.connectMempool loop Every Frame (vsync ≈ 60 Hz) RT->>RT: glfwPollEvents · FPS calc RT->>SP: statsReceiver.update() → extract snapshot RT->>RT: ImGui build · glClear · RenderDrawData RT->>FP: frameSender.reserve() RT->>RT: glReadPixels into slot.pixels · vertical flip RT->>RT: glTexImage2D(previewTex) RT->>FP: frameSender.deliver() RT-->>CV: frameCv.notify_one() RT->>RT: glfwSwapBuffers end loop Net receive loop NT->>CV: wait_for(lk, 200 ms) CV-->>NT: woken by notify or timeout NT->>FP: frameReceiver.update() alt hasNewData NT->>FP: getData() → FrameData* NT->>NT: send_frame(fd, pixels, w, h) NT->>SP: deliverStats(bytesSent, framesSent, addr) NT->>FP: cleanup() else no new frame NT->>FP: cleanup() end end

Zero-copy frame transfer: The render thread writes pixels directly into the reserved Mempool slot (glReadPixels targets slot→pixels.data()). No copy is made — the net thread reads the same memory via getData(). The Mempool ref-count keeps the slot alive until cleanup() is called.

Latest-wins drop policy: If the render thread produces a second frame before the net thread consumes the first, the new slot replaces the pending slot in g_frameReceiver. The older slot's ref-count reaches zero and is immediately recycled by the pool. The net thread always sends the newest frame.

3Client Thread Model

3a. Net Thread → FrameData ports → Render Thread (sequence)

sequenceDiagram autonumber participant NT as Net Thread participant FP as Frame Port participant SP as Stats Port participant RT as Render Thread Note over NT: Setup — frameSender.connectMempool, statsSender.connectMempool Note over RT: Setup — frameReceiver.connect, statsReceiver.connect RT->>NT: Click Connect — g_serverIp/Port set, g_doConnect=true NT->>NT: socket() · inet_pton() · connect() NT->>SP: deliverStats(connected=true, "Connected") loop Per Frame (net thread) NT->>NT: recv_all(hdr, 12 B) NT->>FP: frameSender.reserve() NT->>NT: recv_all(pixels) into slot.pixels NT->>FP: frameSender.deliver() NT->>SP: deliverStats(bytesRecv, fps, frames) end loop Render Loop (~vsync) RT->>FP: frameReceiver.update() alt hasNewData FP-->>RT: const FrameData* RT->>RT: glTexImage2D or glTexSubImage2D RT->>FP: cleanup() else no new frame RT->>FP: cleanup() end RT->>SP: statsReceiver.update() → extract → cleanup() RT->>RT: ImGui panels · RenderDrawData · glfwSwapBuffers end NT->>NT: recv fails → close_sock · g_doConnect=false NT->>SP: deliverStats(connected=false, "Disconnected")

Zero-copy recv: The net thread calls g_frameSender.reserve() before receiving pixels, then passes slot→pixels.data() directly to recv_all(). Pixels land in the Mempool slot without an intermediate buffer.

No condvar on client: The render thread polls frameReceiver.update() every vsync. The render loop runs regardless — it displays the last good texture when no new frame has arrived. A condvar would add complexity with no benefit here.

4End-to-End Frame Pipeline

Zero-copy path: On the server, glReadPixels writes directly into the Mempool slot. On the client, recv_all writes directly into the Mempool slot. Neither side makes an intermediate copy — pixels land once in pre-allocated memory and are consumed in-place.

5Wire Protocol — Frame Format

Client enforces len ≤ 64 MB before allocating the Mempool slot to guard against corrupt headers causing runaway allocations. If the pool is exhausted, the client drains the socket bytes to stay in sync but skips the GL upload for that frame.

6Server Render-Loop Step Ordering

The data-port capture step wraps the glReadPixels call. All steps must stay in this order.

Correct Order (implemented)

1
glfwPollEvents · FPS calc · statsReceiver.update()
Poll window events; pull latest stats from net thread via data ports
2
ImGui build + ImGui::Render
Builds ImGui draw lists in CPU memory; no GL calls yet
3
glClear + ImGui_RenderDrawData
Emits all OpenGL draw calls — back buffer now has the current frame
4
g_frameSender.reserve() — get Mempool slot
Acquires a free pre-allocated pixel buffer from the pool
5
glReadPixels → slot.pixels ← CAPTURE
Reads fully rendered back buffer directly into the Mempool slot. Stalls GPU until all draw commands finish.
6
Vertical flip · glTexImage2D(previewTex)
CPU flip while slot is still owned by sender; preview uploaded before deliver
7
g_frameSender.deliver() · g_frameCv.notify_one()
Transfer slot ownership to net thread; signal condvar to wake it
8
glfwSwapBuffers
Swaps back→front. Back buffer is now undefined until next glClear.

Why Order Matters

If glReadPixels placed…Result
Before glClearReads previous frame — one frame behind
After glClear, before RenderDrawDataReads cleared (blank) framebuffer
After RenderDrawData, before SwapBuffers✓ Current fully rendered frame
After SwapBuffersFront buffer — undefined on many drivers
Preview upload before deliver: glTexImage2D(previewTex) uses slot→pixels.data() before calling deliver(). Once deliver() is called, the slot is owned by the receiver and must not be read. The GL call is synchronous so this ordering is safe.

Pool sizing rationale (3 slots): At steady state one slot is active in the receiver, one is pending (latest delivered), and one is being filled by the producer. A 3-slot pool ensures the producer never blocks. The 2-slot stats pool is sufficient because stats updates are infrequent relative to frame delivery.
