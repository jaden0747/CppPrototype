Teaching Note This Codebase

How Sockets and TCP Work

This document explains the mental model first, then walks through how the streaming prototype uses TcpListener, TcpConnection, frame headers, and endpoint threads.

1. The Mental Model

Socket

A socket is one endpoint of a network conversation. In code, it behaves like a handle you can read from and write to.

IP Address

The machine location. Example: 127.0.0.1 means "this same computer".

Port

The application doorway on that machine. Example: port 9999 is where the stream server waits.

TCP

A reliable byte stream. It preserves byte order, retransmits lost data, and tells you when the connection breaks.

Brain interaction: imagine two programs sharing a very long pipe. One side pushes bytes in. The other side receives those same bytes in the same order. TCP does not know what a frame, image, header, or JSON message is. It only knows bytes.

Connected Socket

After accept/connect succeeds, both programs hold a connected socket. That is the thing used for read and write.

If TCP is reliable, why do we still need a frame header?
Answer TCP preserves bytes, but it does not preserve message boundaries. If the sender writes "header" then "pixels", the receiver just sees bytes. The app protocol must say how many bytes belong to one frame.

3. TCP Is a Stream, Not a Message Queue

This is the single most important socket lesson. TCP gives you a continuous byte stream. A single write on one side may be received as several reads, or several writes may be combined into one read.

Sender's intention

write 16-byte header
write 2,764,800-byte RGB payload

Receiver may observe

read gets 7 bytes
read gets 9 bytes
read gets 1448 bytes
read gets 1448 bytes
...
read eventually gets all payload bytes
Teacher warning: never assume one read equals one frame. That mistake works in small tests and fails under real network timing. This codebase correctly uses exact-size reads and writes.

4. What read_exact and write_exact Do

The wrapper in src/stream/tcp_socket.cpp uses Asio composed operations: asio::read(... transfer_exactly(size)) and asio::write(... transfer_exactly(size)).

Function Meaning Why it matters
read_exact(dst, size) Keep reading until exactly size bytes are placed into dst, or an error occurs. Lets frame code safely read a complete 16-byte header or complete image payload.
write_exact(src, size) Keep writing until exactly size bytes from src are sent, or an error occurs. Prevents partial frame headers or partial image payload writes from being treated as success.
close() Shutdown both directions, then close the socket. Unblocks waiting operations and releases OS resources. 
bool TcpConnection::read_exact(void* dst, size_t size)
{
    asio::error_code ec;
    asio::read(socket, asio::buffer(dst, size), asio::transfer_exactly(size), ec);
    return !ec;
}
If the receiver needs 16 bytes for a header but the kernel has only 5 bytes ready, what should happen?
Answer read_exact waits internally until the remaining 11 bytes arrive, or returns false if the connection fails.

TcpListener: the server doorway

TcpListener wraps Asio's tcp::acceptor. The constructor opens an IPv4 acceptor, binds it to a port, starts listening, and puts it in non-blocking mode. 

tcp::endpoint endpoint(tcp::v4(), port);
acceptor.open(endpoint.protocol(), ec);
acceptor.set_option(tcp::acceptor::reuse_address(true), ec);
acceptor.bind(endpoint, ec);
acceptor.listen(asio::socket_base::max_listen_connections, ec);
acceptor.non_blocking(true, ec);
Why non-blocking accept? The server thread must periodically check whether the app is shutting down. A permanently blocking accept could make shutdown awkward. This code polls until a deadline, sleeps 10 ms between "not ready" attempts, and returns std::nullopt if no client appears in time.

connect_tcp: the client dialing function

The client resolves a host string and port into one or more network endpoints, then asks Asio to connect to one. 

tcp::resolver resolver(conn->io);
auto endpoints = resolver.resolve(host, std::to_string(port), ec);
asio::connect(conn->socket, endpoints, ec);

For 127.0.0.1:9999, this usually resolves directly to the local machine's loopback address and the stream server port.

6. Application Protocol: Turning Bytes Into Frames

TCP gives the project a byte pipe. The stream protocol gives those bytes meaning. This project sends each frame as: 

[4B width][4B height][1B pixel format][1B compression][2B reserved][4B payload size][payload bytes]

The fixed header is 16 bytes. The payload is currently raw RGB pixels. H264 exists only as a placeholder enum for future work.

Layer File Responsibility
Frame model include/stream/frame.hpp Defines Frame, PixelFormat, Compression, and payload validation.
Header codec src/stream/frame_protocol.cpp Encodes and decodes the 16-byte wire header.
Frame I/O src/stream/frame_io.cpp Writes header + payload, reads header, reads payload, or drains payload.
TCP wrapper src/stream/tcp_socket.cpp Owns exact byte reads/writes, connection creation, listener accept, and close behavior.

Sending one frame

write_frame(conn, frame)
  validate frame
  header = header_from_frame(frame)
  bytes = encode_header(header)
  conn.write_exact(header bytes)
  conn.write_exact(frame.pixels)

Receiving one frame

read_frame_header(conn)
  conn.read_exact(16 bytes)
  decode and validate header

read_frame_payload(conn, header, frame)
  resize frame.pixels to payload_size
  conn.read_exact(payload_size bytes)
Brain interaction: cover the payload with your hand and look only at the header. Can you know how many bytes to read next? Yes: payload_size. That is why the receiver can remain synchronized.

7. Server Endpoint Walkthrough

The server endpoint lives in src/stream/stream_server.cpp. It is the bridge between data ports and TCP.

The render thread captures frames with GlFrameCapture. After it delivers a frame into the data port, it calls notify_frame_available(). The server network thread wakes up, promotes the latest frame from the receiver port, validates it, and writes it to the connected client. 

render thread:
  capture framebuffer
  deliver Frame into SenderPort
  endpoint.notify_frame_available()

network thread:
  wait for notification
  frames_.update()
  frame = frames_.getData()
  write_frame(client, frame)
Good design choice: TCP code does not know about OpenGL. OpenGL code does not know about socket handles. The endpoint is the adapter between them.

8. Client Endpoint Walkthrough

The client endpoint lives in src/stream/stream_client.cpp. It waits for a UI connect request, opens a TCP connection, reads frames, and delivers them into a data port for the render thread.

Connect request

UI calls connect

Dial server

connect_tcp

Read header

16 exact bytes

Reserve frame

mempool slot

Read payload

direct into slot

Frame* slot = frames_.reserve();
if (slot) {
    read_frame_payload(conn, header, *slot);
    frames_.deliver();
} else {
    drain_frame_payload(conn, header);
}

Why drain when the frame pool is exhausted?

Suppose the client reads a valid header saying "the next payload is 2,764,800 bytes", but it has no free frame slot. It cannot simply skip reading. If it left those bytes in the TCP stream, the next header read would accidentally read image pixels and the protocol would be corrupted.

Rule: after reading a header, the receiver must consume exactly that payload, either into a frame slot or into a temporary drain buffer.

9. Threading and Shutdown

Object Thread behavior Shutdown mechanism
StreamServerEndpoint Owns one network thread that listens, accepts, waits for frames, and writes them. stop() clears running_, closes active sockets, notifies the frame condition variable, then joins.
StreamClientEndpoint Owns one network thread that waits for connect requests, connects, and reads frames. stop() clears flags, closes the current connection, wakes the request condition variable, then joins.
TcpConnection Used by one endpoint thread at a time in this design. Destructor calls close(), giving RAII cleanup.
Why does stop() close the socket instead of only setting a boolean flag?
Answer A thread may be blocked inside a read, write, accept, or wait. Closing the socket forces network operations to return, so the thread can observe the stop flag and exit.

10. Why ignore_sigpipe() Exists

On POSIX systems, writing to a closed socket can raise SIGPIPE, which may terminate the process by default. The helper in tcp_socket.cpp ignores that signal so socket write failures come back as normal errors instead. 

void ignore_sigpipe()
{
#ifndef _WIN32
    ::signal(SIGPIPE, SIG_IGN);
#endif
}

Final mental checkpoint: when debugging a stream bug, ask which layer owns the problem: frame validity, protocol header, exact byte transfer, endpoint thread state, data-port handoff, or OpenGL texture upload. That question cuts the search space sharply.

13. Common Bugs This Design Avoids

Bug Symptom Design protection
Assuming one read equals one frame Corrupted frames or random disconnects read_exact and explicit payload sizes
Protocol desynchronization after dropping a frame Next header parse fails drain_frame_payload
Socket details leaking into UI Hard-to-change app code TcpConnection, StreamServerEndpoint, StreamClientEndpoint
GL code running on network thread Context errors or crashes GL adapters are used by the render thread; endpoints use data ports
Hung shutdown App window closes but process stays alive Endpoint stop() closes sockets and wakes condition variables
